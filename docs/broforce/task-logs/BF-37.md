## Implemented policy

The four frozen normal game IDs dispatch before generic settlement, even when a Broforce engine produces missing or misleading co-op metadata. Registration must resolve the exact ID to engine `broforce` with `stageId === game.id`. A non-Broforce game cannot use a forged Broforce envelope to obtain a Broforce award.

Board games grant only BF-27's exact per-owner devil and its +6 XP per actual new recruit. No score-based reward, board points/wins, generic XP/played/best credit, dry-streak changes, pool recruit, Bond substitution, journey/progression, mutation bonus, survival/boss grant or shared-roster addition. Arcade/dev Broforce grants no profile progression and writes no transaction. Existing non-Broforce settlement remains intact.

Normal board closure is retained: show a source-branded result with the original label and scores, selected portraits, and separate Sean/Amber recruit cards; then advance the turn once, or return to rolling for an item action with `returnToRoll`. ## Persistence protocol and recovery

1. Before engine start, save `run.pending.bfAttempt`: schema, random 160-bit attempt ID, stage/game ID, independent numeric seed, board origin, fixed owner order, selected fighter IDs and BF-17's `chooseDevil` result. Crypto randomness does not consume the board RNG. Resume reuses the saved attempt instead of resetting it. A legacy game pending without attempt metadata starts a new attempt; a legacy result never gains reward authority.
2. The host verifies the saved attempt against its captured session attempt, registered descriptor and separately captured BF-21 extraction evidence. It stages `run.phase='result'`, normal result fields, `bfAttempt` and `bfIntent` before profile IO. Terminal payload fields are copied explicitly; extra developer-supplied owner/origin fields cannot override policy inputs.
3. Invoke real `planBroforceAwards` / `applyBroforceAwards`. Save the complete resulting profile **once**, with both rosters, earned unlocks, XP and BF-27 receipts in the same serialized object. Do not mutate the live profile or show a saved recruit until that write succeeds. Preserve the photo library's nonenumerable selected pair and existing earned-unlock reasons.
4. Acknowledge the result with `bfCommitted`/`bfGrants`. These are display caches, never grant authority. If acknowledgement fails, the atomic profile receipts remain authoritative. Recovery through `presentResult` revalidates the durable attempt/intent and replays BF-27 idempotently. The original `app.js:continueRun` result branch reaches this recovery without a caller edit; its game branch reaches preserved-attempt restart. Direct `requestGame({resume:true})` also routes a pending intent to result recovery.

`writeDurableJSON` / `readDurableJSON` deliberately bypass the old `writeJSON` memory fallback. Legacy callers retain their existing fallback behavior. Attempt-save failure prevents the engine from starting. Intent-save failure prevents profile IO; profile-save failure retains the recoverable intent and shows a retry-only dialog. No failed write is reported as durable. Leaving through Home invalidates the launcher and preserves pending state via the existing host save; if storage remains denied, export a backup before closing. A crash **before** a successful intent write can only restart the saved attempt, not recover an unsaved victory. A crash after intent save replays the claim, and a crash after profile save cannot duplicate XP/recruits. Acknowledgement failure does not roll back a durable profile.

Profile version remains **20**. Optional `broforceClaims` validation checks the BF-27 key, owner, catalog ID, attempt syntax, 4096-receipt cap, and single devil identity across the attempt. Corrupt maps are quarantined with persistent `broforceClaimsBlocked`, rather than silently reopening claim keys. Other profile progress remains loadable; restore a verified backup to repair corrupt receipts. The cap is not pruned because pruning would reopen old claim IDs. A saturated map fails closed.

BF-34/PM must use `s.broforceReward.attempt` for board mission creation: `{attemptId, stageId, seed, devilId}`; initial mission fighters remain the selected `s.players[i].character`. Before setting the frozen terminal envelope and calling `s.finish`, the adapter must submit the actual completed BF-21 extraction state:

```js
const attempt = s.broforceReward?.attempt;
// Board mission creation uses attempt's immutable IDs/seed/devil.
// At an extracted terminal, while the session is still alive:
s.broforceReward?.confirmExtraction({
  devilId: attempt.devilId,
  devilDefeated: true, // must come from the mission's actual defeated-devil state
  extraction: missionExtraction // actual BF-21 completed state, including receipts
});
// Then s.teamResult = {kind:'broforce', won, bf: terminal.bf}; s.finish(...).
```

Use `aliveAtBoarding[i] = !!extraction.receipts[i]` in that terminal envelope. The bridge checks active/completed/extracted/departure state, saved devil identity, fixed player index/owner, and BF-21's boarding interval [2.4, 11.4). It copies evidence before session cleanup; the envelope alone never suffices. Failure/timeout needs no extraction confirmation. Arcade/dev has no reward bridge and the adapter must use its ordinary practice initialization. No eligible devil yields `attempt.devilId === null` and cannot award a character. BF-34 must handle that no-recruit case explicitly.

This is an offline local-browser consistency boundary, **not cryptographic proof of gameplay**. An actor controlling JavaScript or localStorage can fabricate both channels or change saved records. There is no server, signed simulation transcript, cross-tab compare-and-swap, or defense against browser storage deletion/rollback. The supported workflow is one active game/tab. Within it, arbitrary terminal metadata alone, mismatched stages/devils/owners, late callbacks, duplicate finishes and replay cannot confer extra awards.

No fake production modules or edits to `app.js` were introduced. `continueRun` already checks its run/pending/movement token after result display; Home cancels those tokens. Its pre-existing behavior of ignoring a null result return in the absence of a lifecycle change is not generalized or changed here.
