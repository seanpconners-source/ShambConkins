## Integration dependencies / risks

- `prisoners.js` **does not authenticate** arbitrary `fightersByOwner` arrays against a profile. To guarantee locked fighters are never equipped, the owning adapter **must** pass **only** `snapshotFighters(profile, owner)` from BF-17, and separately retain `run.players[i].character` (board-selected character). The existing mission `poolFor` merely checks catalog IDs in its fallback; it is not itself an unlock-verification step. **Adapter call:** `fightersByOwner:{Sean:snapshotFighters(profile,'Sean'),Amber:snapshotFighters(profile,'Amber')}` when constructing the stage's per-owner fighter pools. This is an integration-owner dependency, not a change permitted to BF-48.
- Live attribution must originate from actual BF-14 projectile `impact` and explosion radius/collision results, with a canonical living player index. The scoped pure test exercises `cage-destroyed` intents and geometric blast fan-out, **not** an end-to-end fired bullet, physics sim or explosion VFX. Do not treat synthetic `prisonerId` or an enemy blast as sufficient attribution.
- Stage/world spawn-bounds checks depend on level/world dimensions owned elsewhere. This pure module validates finite x/y and unique IDs; its API does not receive a world rectangle. Stage construction must check cage rectangles remain within the playable world if this is required.
- Rescue events must remain **temporary fighter swaps only**. No profile writes or recruit calls exist in this module; BF-37 exact-devil claims, the real living boarding decision, retry/recovery and no-arcade-reward logic remain under their separate integration/acceptance tests.
- The animation contract is metadata (`animationMs:520`, `statusMs:950`) for the drawing layer; BF-48 did not measure actual animation, frame rate, Android touch input or device rendering.
- No merge into `feature/broforce-wave3-candidate`, `feature/broforce-mobile`, `TESTver` or `main`. Not playable, released, or phone-approved by this scoped task.
