## Interface and behavior

- `planBroforceAwards({profile,origin,attemptId,devilId,boarded,aliveAtBoarding,owners=['Sean','Amber'],won}={})` creates a pure, source-profile-preserving JSON plan. Board-mode victory and actual alive-at-boarding receipts for each owner are mandatory. P1-only, P2-only and both are valid; neither awards nothing.
- `applyBroforceAwards(profile,plan) -> {profile,grants,receipts}` returns a cloned profile. It only adds exact devil ID(s) to the qualifying canonical owner's roster, adds one `broforceClaims` receipt per grant, retains global `earnedUnlocks` reasons already present, and uses the existing `src/profile.js:recruit` standard of +6 XP per **new** grant. It changes neither shared roster nor the selected board-game character.
- Receipt key format: `bf27:` + JSON-stringified `[attemptId,owner]`, with serializable `{attemptId,owner,devilId}` values. Existing matching receipts cause no new grants or XP; attempting to replay the same attempt with a different devil ID throws before mutation. Malformed receipts are rejected.
- Real `src/profile.js:canRecruit(...,'encounter')`, `src/characters.js:characterIdentity`, and `SPECIAL_UNLOCKS` semantics restrict eligibility. The BF-17 `chooseDevil` policy is encounter-based and disallows special-category locks; this module intentionally allows the still-locked owner to receive an exact chosen ID even when the other owner already owns its alias.
- The module intentionally does **not** use `recruit`, `recruitReward`, `saveProfile`, localStorage, generic game reward rolls, or any profile/launcher writes.
