## Reproduced defects and changes

1. **Silent durable false-positive.** Baseline `writeDurableJSON` returned true whenever `setItem` returned, even if a simulated storage layer silently discarded the write. Reproduced against the actual pinned `src/persistence.js` before any change. It now requires `getItem` readback of the identical serialized bytes; failure/denial/throw/missing API returns false without clearing the legacy memory fallback. `writeJSON` retains its existing best-effort memory fallback semantics. Added `inspectDurableJSON` to distinguish missing, unavailable, valid and corrupt stored JSON.
2. **Durable receipt erased by stale memory writer.** Baseline sequence reproduced: save a real exact-owner BF claim durably; fail a regular `writeJSON` for a stale profile (which populates memory fallback); `loadProfile` then returned stale XP 0/no claim; a later successful ordinary `saveProfile` erased the durable receipt and roster. The modified profile loader prefers readable durable version-20 BF state whenever either disk or volatile state contains BF metadata. Saving rejects stale/missing/mutated existing claim receipts or removal of a receipt's exact owner roster character. This affects only profiles with durable Broforce metadata; normal v20 progress remains loadable.
3. **Unparseable durable profile.** Corrupted localStorage JSON previously loaded as a fresh profile and could be overwritten by a subsequent ordinary save. The loader quarantines corrupt raw JSON locally (`broforceClaimsBlocked`); `saveProfile` refuses to overwrite an unreadable/corrupt stored profile. Invalid but parseable Broforce claim maps continue to migrate to the persistent blocked state on a normal profile save so unrelated achievements can still persist.
4. **No reward-policy, origin, stage registry, fighter selection, version, asset or gameplay change.** The only authority for a board attempt or helicopter-verified recruit remains BF-37's launcher/mission bridge and BF-27. The receipt validator is unchanged.

## Constraints, remaining risks and coordination

- `localStorage` cannot provide server-side anti-tamper, remote recovery, cross-tab transactional compare-and-swap or atomic durability under browser/OS data deletion. One active tab/profile is assumed. If storage is corrupt, user restoration from a verified backup is necessary; blindly resetting the blob could reopen replay claims.
- The new strict profile guard intentionally returns `false` rather than clobber durable receipts when an old profile snapshot tries to save. UI features which ignore `saveProfile`'s boolean result may not surface that rejection. BF-37 must continue to use `saveProfile(...,{durable:true})`, persisted attempt/intent and exact proof, and must retry/reload on `false`; no launcher file is owned here.
