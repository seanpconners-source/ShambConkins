## Owned changes

- `src/gameLauncher.js`: do not write a profile again when a Broforce settlement applies **zero fresh owner-specific grants**. Before acknowledging an existing claim, verify that every claim for the same attempt in live profile state is already present identically in durable `PROFILE_KEY` storage. If missing/corrupt, stay in retry instead of guessing. New grants still require a successful durable `saveProfile` **before** mutating in-memory profile or acknowledging the run. Keep result receipts and `returnToRoll` / `endTurn` wiring unchanged.
- `tests/broforce-bf53-settlement.mjs`: new focused adversarial tests. Reuses declarations from the BF-37 host fixture and loads the **actual** launcher, persistence, profile, reward policy, roster and extraction source modules; does not alter the original fixture or pretend to run real browser gameplay. Checks all four stage IDs × P1-only, P2-only, both, neither; stable selected board players and no generic awards; alias/owner unlocks; arcade/dev/failure; zero-grant profile writes; exact settled-result replay after profile-write denial; intent/profile storage denial and crash recovery; duplicate callbacks; return-to-roll/end-turn; cancellation/stale callbacks.

## Defect evidence

Prior launcher `recoverBroforceResult` unconditionally called `saveProfile(applied.profile,{durable:true})`, even when `applyBroforceAwards` produced no fresh grants. Thus a previously successful, durable result replay with newly denied profile storage could show a **Reward save pending** dialog and refuse to reopen the already-settled result. Failed/no-boarder cases also made unnecessary profile writes. BF-53 test reproduces those cases using the real launcher and the BF-37 host fixture. The production change avoids those writes but still checks durable claim receipts before trusting replay.
