# Development workflow for ShambConkins

This guide describes the owner's standing workflow once the initial setup is approved. `AGENTS.md` is the operational instruction; `CLAUDE.md` and `docs/AI_STATE.md` remain the game reference and compact project state. The initial setup itself needs owner approval after a committed diff review. Normal validated work may then move into `TESTver`; `main` release always needs explicit approval.

## Configuration and scope

The checked-in `.codex/config.toml` configures native Codex only: Astra Medium for the PM and Sol Medium with at most three concurrent workers when Codex execution is selected. It does not launch regular ChatGPT chats, select their model, or change their billing. The default task-routing policy is economy-conscious: regular ChatGPT **GPT-6 High** for suitable implementation; Astra Medium for normal coordination, High for difficult planning/integration, and Extra High (`xhigh`, where supported) only exceptionally. Sol Medium/High remains available for CODEX MODE and work that benefits from Codex execution.

Open a trusted local checkout at the project root so Codex can read project configuration. `AGENTS.md` is discoverable only on branches containing it: verify which instructions loaded at startup. Regular ChatGPT workers must explicitly fetch/read repository instructions; do not assume automatic instruction discovery from a GitHub connection. A hosted chat may not load the TOML or change its running model. Native delegation depends on the current tool schema. If that schema requires `fork_turns=none` for a model override, provide a self-contained bounded assignment. This setup adds no custom orchestrator, permission bypass, or unsupported external-chat settings.

During setup, one bounded assignment ran successfully on native Sol Medium. Runtime Codex CLI project-config discovery remained unverified because the runtime home was read-only; verify it in a trusted local checkout before claiming it works there.

The owner can send rough notes. The PM turns them into actionable tasks, investigations, decisions, future ideas, and deferred or rejected items. Treat actionable notes as implementation requests unless he asks for planning or research only; speculative ideas do not authorize implementation. Inspect callers, dependencies, acceptance criteria, and risks, then batch independent tasks so difficult work does not delay easy work. Avoid unrelated refactoring and new dependencies. Ask only when gameplay intent is materially ambiguous, an architecture choice has a meaningful tradeoff, an action is destructive or high risk, or a production release is ready for approval. The PM remains responsible for every delegated result.

## Economy Mode and ChatGPT batches

`ECONOMY MODE`, `Save Credits`, `Use ChatGPT`, `Delegate to ChatGPT`, and `Prepare ChatGPT Tasks` prioritize standalone regular ChatGPT High assignments. `CODEX MODE` requests the native Astra/Sol workflow. Honor an explicitly selected mode; explain why a tool limitation or safety requirement needs an exception. Do not convert a routine Economy Mode assignment into a paid native worker merely because native delegation exists.

For each task, inspect the actual relevant implementation and assess objective, affected files/systems, dependencies/conflicts, acceptance criteria, complexity/risk, and tool needs. Most bounded fixes, CSS/UI/text/asset/content changes, documentation, reviews, isolated JavaScript/gameplay changes, and well-defined moderate features belong with ChatGPT High when its GitHub tools can implement them reliably. Reserve Codex for difficult interconnected state, large iterative systems/refactors, demanding executable testing, architecture, regressions, or branch conflicts; independent portions may still go to ChatGPT. Reliable integration via GitHub tools plus verified CI does not inherently require Codex.

Prepare all practical independent prompts at once using [CHATGPT_HIGH_ASSIGNMENT_TEMPLATE.md](CHATGPT_HIGH_ASSIGNMENT_TEMPLATE.md). Each completed prompt includes repository, exact TESTver base SHA, unique branch, context, relevant paths, behavior/acceptance criteria, safety/validation, and delivery requirements. Identify which can run simultaneously and which must wait; overlapping shared files or dependent features normally run sequentially. Record assignments in [DEVELOPMENT_TASKS.md](DEVELOPMENT_TASKS.md), keeping prepared, reported, remotely verified, integrated, and phone-approved states distinct. The PM alone maintains shared tracking/state to reduce conflicts.

Use `CHATGPT HIGH ASSIGNMENTS`, `CODEX ASSIGNMENTS`, `INTEGRATION PLAN`, and `NEXT ACTION` when presenting a workload. Include one full copy-ready prompt per external task, a capability reason/model/effort for each Codex task, and exact owner actions. Do not require an Astra visit for every worker. Ordinary batch flow:

1. PM prepares the complete batch. The owner opens regular GPT-6 High conversations and pastes each independent prompt.
2. Each worker checks its own model/tools/GitHub access, implements on its assigned feature branch, validates what it can, and reports actual commits and limitations. No shared context between chats is assumed.
3. The owner returns the branch names together. The PM reads actual GitHub commits/diffs/CI, checks conflicts and dependencies, and requests corrections where needed; a branch list is sufficient to begin review.
4. The integration manager validates the combined candidate and advances TESTver using the existing safe workflow. Independent ready features need not wait for blocked work. The owner then playtests on the Samsung phone; main still needs explicit release approval.

Notes may also go directly to ChatGPT High: follow the same instructions, create isolated task branches, report results, and register returned branches when integration is requested. An implementation worker never inherits the PM's standing TESTver integration authority; only a separately authorized integration assignment may use it.

At setup, available tools exposed native Codex subagents and GitHub operations, but no way to create/message regular ChatGPT conversations. External handoff is manual, not simulated. The owner reports separate regular ChatGPT and Codex allowances; this setup cannot verify account billing, quotas, or guarantee savings. Native subagent use is not proof of regular ChatGPT billing. Recommend GPT-6 High for every external task, even small ones; report unavailable High/tools or account limits instead of silently downgrading to Medium. If editing is unsupported, accept a reviewable patch/replacement files with paths and exact base SHA; a patch is not a pushed branch or verified implementation.

## Branch flow

1. Read `CLAUDE.md`, `docs/AI_STATE.md`, `AGENTS.md`, and the relevant code. Inspect status, recent commits, `main`, `TESTver`, remote movement, and owner changes. The setup baseline was `3ad8cafaa446c1d988309eee6298fc0d4531b67b` on `main` and `TESTver`; treat it as history, not as a perpetual branch tip.
2. Create a feature or fix branch/worktree from current `TESTver`. Assign independent files to parallel workers; use separate worktrees when work may overlap. Keep owner art and uncommitted edits intact. Do not force-push, reset, rewrite history, or discard owner work. Rebase only a private feature branch where appropriate; use ordinary merges on shared `TESTver`.
3. Implement and review the bounded change. Run focused checks, `npm run build`, and `npm test` as appropriate. Read logs for errors even when commands exit zero. For UI/game changes, inspect Playwright screenshots at 390×780 and 1100×700. Record what was not tested, including real-phone feel.
4. Commit the feature. Make a candidate against the latest `TESTver`, review the combined diff, and validate that candidate before advancing the remote branch. If `TESTver` moved, merge the new tip into the candidate and revalidate. If local checks cannot run, leave the branch isolated or verify successful CI for the candidate's exact SHA. Green automation does not mean the owner approved gameplay.
5. Push validated `TESTver` without force, verify its remote SHA, and tell Sean to open the `TESTver` shortcut. If integration or validation fails, preserve the feature branch and leave the remote at its last good commit. Keep the Android `TESTver` endpoint at `http://127.0.0.1:8766`; its browser storage is separate. Preserve both Android launchers, including production. Update `docs/AI_STATE.md` after meaningful game work with current facts and next steps, without a transcript.

## Development validation

`.github/workflows/development-validation.yml` defines push checks for `TESTver`, `codex/**`, `feature/**`, `fix/**`, and `integrate/**`, and pull-request checks targeting `TESTver`. It uses read-only `contents` permission, never releases or pushes, runs module/build/full tests, and sets up Node 22 and Playwright 1.50.1 at the same expected browser paths as the existing Castlevania workflow. It checks smoke and route logged results in addition to command exit codes and retains logs/screenshots for 14 days. `tests/games.mjs` exception accounting is imperfect, so a green run does not establish exhaustive gameplay correctness. Verify CI success on the exact candidate SHA before relying on it; a checked-in workflow alone is not proof it ran. The existing Castlevania workflow is unchanged.

## Production release

Before asking for release approval, compare `main` and `TESTver` with the owner's accepted scope. Exclude rejected changes through separate branches or reversions, preserving public history. Prepare the established release materials: `src/version.js`, `package.json` version and release output path, changelog, and release HTML. Run `npm run release` only for approved production preparation. Generated offline HTML may exceed GitHub's 100 MB file limit: for v0.58.3 distribute it as a versioned GitHub Release asset after verifying the compiled HTML, rather than committing the oversized artifact or replacing original art. Show the concrete candidate and validation for approval before advancing `main`. After an approved release, bring `TESTver` forward without losing ongoing work. These are workflow rules, not GitHub branch protection; `main` and `TESTver` were unprotected at setup time.

## Report and session handoff

Report under `COMPLETED`, `TESTVER STATUS`, `TEST RESULTS`, `REMAINING`, `NEXT STEP`, `SESSION RECOMMENDATION`, and `RECOMMENDED MODEL`. Say which SHA was validated and whether work is local, pushed, or merged. Recommend a fresh session when context is confused, the next task enters a substantially different complex system, a major project is complete, or a hard bug needs clean context. Give a compact handoff at that point; routine batches need no new session.

At a handoff, give the next session a compact prompt such as:

> Use Astra Medium as PM for ShambConkins in `<ECONOMY MODE or CODEX MODE>`. Start on `<branch>` at `<SHA>`. Read `AGENTS.md`, `CLAUDE.md`, `docs/AI_STATE.md`, and active rows in `docs/DEVELOPMENT_TASKS.md`. Objective: `<approved objective>`. Completed: `<commits and validation>`. Pending: `<tasks, returned branches, dependencies>`. Watch for: `<risks or owner decisions>`. Prefer standalone GPT-6 High assignments in Economy Mode; use native Sol Medium/High where Codex capabilities are needed or CODEX MODE is requested. Inspect returned branches yourself, validate the combined candidate, and follow TESTver integration authority. Never advance main without explicit release approval.

Fill the PM handoff above before recommending a fresh Astra session. For every fresh external worker conversation, provide the complete filled ChatGPT assignment template, not this PM prompt or merely a link to a file. Stay in the current PM conversation for related work unless a fresh context materially helps.
